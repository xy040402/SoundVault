# 音匣 v1.0.2 — 修改意见与方案

> v1.0.1 已冻结（源码、说明书、安装包都留在 `v1.0.1/`，不再改动）。
> 这个版本只做一件事：**P2 大库导入性能**。别的需求先记在这里，不插队。

## 已完成

### P2｜大库导入极慢（3000 个文件 10 分钟）（✅ 完成）

**现象**（社区反馈）：一个 3000 文件的素材包，第一次导入要等 10 分钟以上，期间界面像卡住；
磁盘占用大的库（长时间环境声、96k/24bit）更明显。

**根因**：扫描时**为了画波形把每个文件从头读到尾**。

```
v1.0.1 的扫描流程（每个变更文件）：
  读文件头（几 KB） + 读全部采样 → 算 512 点峰值 → 写库
  ↑ 这一行是全部开销：读的量 = 整个库的字节数
```

扫描耗时基本正比于**库的总字节数**。1.48 GB / 60 个 5 分钟 WAV 实测：

| 版本 | 扫描用时 |
|---|---|
| v1.0.1 | **1709 ms** |
| v1.0.2 | **20 ms** |

按这个比例，30 GB 的库在机械盘/网络盘上就是几分钟 —— 和社区的"10 分钟"对得上。

**改法：两阶段索引**

| 阶段 | 做什么 | 何时 |
|---|---|---|
| ① 快扫 | 只读文件头（采样率 / 声道 / 位深 / 时长），**不算波形**，整库一次事务写库 | 导入、启动增量扫描 |
| ② 补波形 | 查 `peaks IS NULL` 的行，按批（200 个一批）解码算峰值，一批一个事务写回 | 扫描结束后自动在后台跑 |

配套改动：

| 位置 | 改动 |
|---|---|
| `Indexer.ReadFile` → `ReadHeader` | 去掉 WAV / AIFF 的波形计算 |
| `Indexer.FillPeaksAsync` | 新增：后台补波形，并发限制 `min(3, 核数/2)`，共用进度条与取消按钮 |
| `IndexDb.PeaksMissingCount / PeaksMissing / SetPeaks` | 新增：待补数量、取一批路径、批量写回 |
| `MainWindow.ScanLibrariesAsync` | 所有库扫完后统一补波形（避免第二个库等第一个补完） |
| `MainWindow.ScanRootAsync`（导入单个库） | 卡片先出来，波形后台补 |

**修正：补波形不能挡在"出现之前"**

第一版把 `FillPeaksAsync` 塞在 `ScanRootAsync` 里，而建库发生在它后面 —— 结果还是"补完才显示"。
现在的顺序：

```
扫描（20ms） → 建库 + 切视图（用户开始用） → 后台补波形（进度条同时显示）
```

实测时间线（40 个 5 分钟 WAV，约 1 GB）：

| 时间 | 事件 |
|---|---|
| 45.156 | 扫描完成 total=40 用时=20ms |
| 45.196 | **已加入左栏** 文件数=40（卡片出现） |
| 45.211 | 开始补波形 待补=40 |
| 46.973 | 补齐完成 用时=1761ms |

截图确认：卡片已经显示，进度条同时是「正在补齐波形 22 / 40 56%」，波形区先是平线，补完自动变真波形。

**进度条改成两行**

| 行 | 内容 |
|---|---|
| 第一行 | 正在做什么 + 能不能继续操作：「正在补齐波形图，您可以继续操作」 |
| 第二行 | `22 / 40　56%　·　剩余 3 秒　·　长音效_10.wav` + 进度条 + 取消 |

各阶段的头部文案：枚举「正在枚举文件，请稍候」、比对「正在比对索引…」、
读头「正在读取音频头（只读文件头，很快）」、写库「正在写入索引…」、补波形「正在补齐波形图，您可以继续操作」。

顺带把旧文案「正在读取音频头**与波形**」改掉了 —— 现在这一步只读头，名字里不该再提波形。
**行为上的变化**

- 导入 3000 个文件：**库立刻可用**（秒级），波形在后台慢慢补，顶部进度条显示 `正在补齐波形 x / y`，可以取消
- 补的过程中卡片已经在，波形区先是平线，补完自动重画
- 第二次启动完全跳过（`new=0 changed=0 skip=全部`，实测 10 ms）
- 老库升级上来：v1.0.1 已经存过波形，`peaks` 不为空，**不会重算**

**实测（1.48 GB / 60 个 5 分钟 WAV）**

| 指标 | v1.0.1 | v1.0.2 |
|---|---|---|
| 扫描（库可用） | 1709 ms | **20 ms** |
| 补波形 | — | 2512 ms（后台） |
| 第二次启动 | 10 ms | 10 ms |
| 峰值落库 | 扫描时 | 后台写入，`PeaksMissingCount=0` 后不再重算 |

### P6｜文件夹和音效同时显示（✅ 完成）

**现象**：一个目录里既有子文件夹、又直接放着音频时，库视图**只显示文件夹卡片**，根目录那些音频要切到「全部音效」才看得到。
用户问"能不能同时显示"——以前是二选一，从没测过。

**根因**：`ShowLibrary` 里是 if/else ——

```csharp
if (children.Count == 0) { 读根目录音频 → 显示音频 }
else { 只显示文件夹，不读根目录音频 }
```

而子文件夹视图（`OpenFolder`）本来就是两段都显示，只是库根这条路径漏了。

**改法**：库根也读 `FilesInDir(root)`，两段一起画：

```csharp
SetAssets(rootRows);
ApplyContentLayout(showFolders: children.Count > 0, showAssets: rootRows.Count > 0);
```

布局本来就支持：文件夹区高度 `Auto`（最多 182px ≈ 两行，多了自己滚动），音频区 `*` 占满剩下的。
统计文案也跟着分情况：`3 个文件夹 · 5 个音效（根目录）`。

顺带给文件夹视图也补了合并统计（以前只写「2 个音效」，看不出里面还有个文件夹）。

**实测**（目录：根目录 5 个 wav + 三个子文件夹；`武器` 里既有 2 个 wav 又有子文件夹 `_近战`）

| 位置 | 统计 | 显示 |
|---|---|---|
| 库根 | `3 个文件夹 · 5 个音效（根目录）` | 上排 3 张文件夹卡片 + 下面 5 张音频卡片 ✅ |
| 武器 | `1 个文件夹 · 2 个音效` | 近战 卡片 + 刀_01 / 刀_02 ✅ |

### P4｜AI 自动识别音频并打标签（❌ 已移除）

**做过一版**：YAMNet（AudioSet 521 类）ONNX，本地推理，右键批量打中文标签，可撤销。链路、性能都正常
（单个 10–100 ms），模型也能正确认出**真实录音**里的雨声、鸟叫。

**为什么撤掉**：实际用下来**准确率不够**。最典型的一次：拔刀的音效被识别成「玻璃破碎」。
音效库里大量是「拟音 / 合成 / 处理过」的声音，不在 AudioSet 的分布里，模型只能瞎猜。
给用户一堆错标签，比没有标签更糟 —— 还得手动删。

**处理**：整个模块连模型一起删掉，不留开关。

| 删掉的东西 |
|---|
| `Services/AudioTagger.cs`（推理 + 521 类中文映射）|
| `MainWindow.AiTag.cs`（批量打标 + 撤销）|
| 右键菜单「AI 识别标签」「撤销 AI 标签」|
| `Microsoft.ML.OnnxRuntime` 包、`Assets/models/yamnet.onnx`（15 MB）+ 类别表 |
| 说明书里的 AI 一节与右键菜单那一行 |

exe 从 93.2 MB 回到 **73.4 MB**。

**教训**：通用音频分类模型 ≠ 音效检索。真要做，得用音效库自己的语料训练（或者做"相似音效"检索，
而不是语义分类）。这条不再排期。
### P3｜能不能像 Everything 一样秒搜（✅ 完成）

**以前**：每次按键都 `ReadAllRows()` 读全库（含峰值 BLOB）→ 建 2 万个卡片对象 → 全量过滤 + 排序。
2 万文件实测：进入搜索 150 ms、拼音首查 **49 ms**；到 10 万就是数百毫秒，打字会一顿一顿。

**改法**（`MainWindow.Search.cs`）：
| 项 | 做法 |
|---|---|
| 整库缓存 | `SearchItems()` 按「库 + 数据版本号」缓存卡片；换库、扫描完成、导入、删库时 `BumpDataVersion()` 失效 |
| 拼音预热 | 建缓存时 `Parallel.ForEach` 把 `PinyinInitials / PinyinFull` 都算好，避免第一次打拼音卡一下 |
| 增量过滤 | 新关键字是上一次的前缀、且排序/收藏没变 → 只在上一批结果里再筛 |
| 输入防抖 | 110 ms 的 `DispatcherTimer`，连打几个字只算一次 |

**实测（2 万文件，每项跑 5 次）**

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 首次进入搜索 | 150 ms | 9.8 ～ 64.5 ms（含 JIT/布局，之后稳定） |
| 再次进入搜索（缓存命中） | 150 ms | **9 ms** |
| 拼音『bd』 | 49 ms | **0.9 ms**（最快）/ 12.8 ms（含 GC 噪声） |
| 增量『拔』→『拔刀』 | 7 ms（每次全库） | **0.7 ms** |
| 全库重筛『拨』 | 8 ms | 0.0 ～ 12.8 ms |

**已知**：首次进搜索仍要读一遍全库（2 万条 ≈ 10–60 ms）；10 万级约 50–300 ms，之后都是毫秒级。
再快就得把搜索下推到 SQLite（FTS5 trigram），目前的体感已经够用，先不做。
