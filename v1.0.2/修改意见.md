# 音匣 v1.0.2 — 修改意见与方案

> v1.0.1 已冻结（源码、说明书、安装包都留在 `v1.0.1/`，不再改动）。
> 这个版本只做一件事：**P2 大库导入性能**。别的需求先记在这里，不插队。

---

## 已完成

### P2｜大库导入极慢（3000 个文件 10 分钟）（✅ 完成）

**现象**（社区反馈）：一个 3000 文件的素材包，第一次导入要等 10 分钟以上，期间界面像卡住；
磁盘占用大的库（长时间环境声、96k/24bit）更明显。

**根因**：扫描时**为了画波形把每个文件从头读到尾**。

```
v1.0.1 的扫描流程（每个变更文件）：
  读文件头（几 KB） + 读全部采样 → 算 512 点峰值 → 写库
  ↑ 这一行是全部开销：读的量 = 整个库的字节数
```

扫描耗时基本正比于**库的总字节数**。1.48 GB / 60 个 5 分钟 WAV 实测：

| 版本 | 扫描用时 |
|---|---|
| v1.0.1 | **1709 ms** |
| v1.0.2 | **20 ms** |

按这个比例，30 GB 的库在机械盘/网络盘上就是几分钟 —— 和社区的"10 分钟"对得上。

**改法：两阶段索引**

| 阶段 | 做什么 | 何时 |
|---|---|---|
| ① 快扫 | 只读文件头（采样率 / 声道 / 位深 / 时长），**不算波形**，整库一次事务写库 | 导入、启动增量扫描 |
| ② 补波形 | 查 `peaks IS NULL` 的行，按批（200 个一批）解码算峰值，一批一个事务写回 | 扫描结束后自动在后台跑 |

配套改动：

| 位置 | 改动 |
|---|---|
| `Indexer.ReadFile` → `ReadHeader` | 去掉 WAV / AIFF 的波形计算 |
| `Indexer.FillPeaksAsync` | 新增：后台补波形，并发限制 `min(3, 核数/2)`，共用进度条与取消按钮 |
| `IndexDb.PeaksMissingCount / PeaksMissing / SetPeaks` | 新增：待补数量、取一批路径、批量写回 |
| `MainWindow.ScanLibrariesAsync` | 所有库扫完后统一补波形（避免第二个库等第一个补完） |
| `MainWindow.ScanRootAsync`（导入单个库） | 卡片先出来，波形后台补 |

**修正：补波形不能挡在"出现之前"**

第一版把 `FillPeaksAsync` 塞在 `ScanRootAsync` 里，而建库发生在它后面 —— 结果还是"补完才显示"。
现在的顺序：

```
扫描（20ms） → 建库 + 切视图（用户开始用） → 后台补波形（进度条同时显示）
```

实测时间线（40 个 5 分钟 WAV，约 1 GB）：

| 时间 | 事件 |
|---|---|
| 45.156 | 扫描完成 total=40 用时=20ms |
| 45.196 | **已加入左栏** 文件数=40（卡片出现） |
| 45.211 | 开始补波形 待补=40 |
| 46.973 | 补齐完成 用时=1761ms |

截图确认：卡片已经显示，进度条同时是「正在补齐波形 22 / 40 56%」，波形区先是平线，补完自动变真波形。

**行为上的变化**

- 导入 3000 个文件：**库立刻可用**（秒级），波形在后台慢慢补，顶部进度条显示 `正在补齐波形 x / y`，可以取消
- 补的过程中卡片已经在，波形区先是平线，补完自动重画
- 第二次启动完全跳过（`new=0 changed=0 skip=全部`，实测 10 ms）
- 老库升级上来：v1.0.1 已经存过波形，`peaks` 不为空，**不会重算**

**实测（1.48 GB / 60 个 5 分钟 WAV）**

| 指标 | v1.0.1 | v1.0.2 |
|---|---|---|
| 扫描（库可用） | 1709 ms | **20 ms** |
| 补波形 | — | 2512 ms（后台） |
| 第二次启动 | 10 ms | 10 ms |
| 峰值落库 | 扫描时 | 后台写入，`PeaksMissingCount=0` 后不再重算 |
