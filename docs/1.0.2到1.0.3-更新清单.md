## 第 1 批 · 高采样率与不规范格式

### 修复：96 kHz / 24bit WAV 点了没声音

- **现象**：导入的素材报 `Unsupported source encoding`，完全放不出。
- **原因**：这类文件用的是 `WAVE_FORMAT_EXTENSIBLE`（fmt 段 40 字节 + 子格式 GUID），NAudio 的 `ToSampleProvider()` 不认。
- **修复**：新增 `Audio/CanonicalWaveStream.cs`，把 Extensible 读成标准 PCM 流再交给播放器；`AudioClip.NormalizeFormat` 统一格式。

### 修复：6 声道文件报块对齐错误

- **现象**：`Must read complete blocks: requested 32768, block align is 12`。
- **原因**：读取块大小不是帧对齐的整数倍。
- **修复**：读取块改成按帧对齐 —— `chunk = 16384 - 16384 % channels`。

## 第 2 批 · 波形生成（issue #1 真凶）

### 修复：「正在补齐波形」永远跑不完（mp3）

- **现象**：mp3 库里进度永远停在补齐，重开接着补，永远补不完。
- **原因**：波形计算**根本没有 mp3 分支** —— 算不出来返回 null，而失败结果**不落库**，于是同一批文件被无限重试。
- **修复**：补上 mp3 解码分支；算不出来也写空数组当"已尝试"标记，不再重试。

### 新增：长 WAV 概略采样

- **原因**：90 秒以上 WAV 每个都全解码，太慢。
- **修复**：`Audio/CoarsePeaks.cs`，超过 60 秒按 128 个时间点跳读；短音效仍全解码保持精确。

### 改进：分批显示 + 进度文案

- 每 200 个一批写库并立刻贴回卡片（`_itemsByPath` 索引避免全表遍历）。
- 文案分「正在继续补齐波形 / 正在补齐波形」，带全库百分比。

### 压测数据（写入文档备查）

| 场景 | 结果 |
|---|---|
| 10 万短 wav | 扫描 2.7 s / 补波形 22 s / 内存 383 MB |
| 1,000 个 90 秒 mp3 | 从前"永远不结束" → 64 s |
| 批次大小实验 | 200 → 50 后 10 万 wav 从 18 s 变 64 s（事务翻 4 倍），改回 200 |

### 修复：波形尾巴被吃掉（关键）

- **现象**：同一个文件，名称列窄时 5 个起伏，拉宽只剩 4 个。
- **原因**：柱子取样用整数步长 —— `per = peaks.Length / target`，`s0 = i * per`，总共只覆盖 `target * per` 个点。宽窗口 `target≈380`、`peaks=512` 时只取样 380 个，**最后 25% 从没画出来**，越宽丢越多（覆盖率 217px→98%、700px→91%、1140px→74%）。
- **修复**：改成按比例映射，保证覆盖整段：

```csharp
int s0 = (int)((long)i * peaks.Length / target);
int s1 = (int)((long)(i + 1) * peaks.Length / target);
```

`WaveformView` 与 `SelectableWaveform` 两处都改。

## 第 5 批 · 波形死循环（用户反馈）

### 现象

导入 4 个文件后「波形图创建不出来」，进度 `a/4` 的 a 涨到 `76348`、`962621`，永远不结束。

### 原因（三连）

1. 那 4 个文件**全是 MP3**，其中 `1. Whoosh Click Loop.wav` 只是扩展名写成了 `.wav`（内容 `ID3` 头）；
2. 1.0.2 的波形计算**没有 mp3 分支**，改名的 `.wav` 按 RIFF 读又抛 `Not a WAVE file`；
3. 失败结果**不落库**，`PeaksMissing` 每轮又把同样 4 个取出来 —— `done` 无限累加。

### 修复

| 改动 | 说明 |
|---|---|
| 按内容判断容器 | RIFF/RF64 → WAV；AIFF/AIFC → AIFF；其它 → 解码器 |
| 解码器挨个试 | 先 `Mp3FileReader`（认 ID3），失败再 `AudioFileReader`；改名文件也能解 |
| 失败计数修正 | 先判 null 再换空数组，日志能真实写 `成功=3 失败=1` |
| **防死循环兜底** | 同一路径只尝试一次（`ConcurrentDictionary`）+ 轮数上限；命中时写日志「这一批都尝试过了，写库没生效」 |

### 验证

| 版本 | 4 个文件 |
|---|---|
| 1.0.2 | `96348/4` … 永不结束 |
| 第 4 批 | `共=4 成功=3 失败=1`（改名的那个是平线） |
| **第 5 批** | **`共=4 成功=4 失败=0，67 ms`** |

## 第 6 批 · 日志体系

### 问题

出问题时只有零星几行日志，看不出**哪个文件在哪个环节**出问题；全量逐文件写又会把日志撑到几十 MB。

### 方案：概括常驻 + 错误常驻 + 详细进黑匣子

| 类型 | 落盘 | 内容 |
|---|---|---|
| 概括 | 立刻 | 操作开始/完成/统计 |
| 失败 | 立刻 | `fail file="…" stage=peaks ms=8 why="…"` |
| 慢 | 立刻 | 单文件 > 300 ms |
| 用户动作 | 立刻 | 入点/出点/清空、标签、评分、收藏、重命名、拖到 DAW、浮窗、导出 |
| 详细 | **只进内存** | 每文件每阶段一行，500 行环形缓冲 |
| 黑匣子 | 触发时 | 失败、卡住、用户导出时整段倒出 |

### 看门狗（治"卡住但不报错"）

每处理完一个文件打一次心跳 `Log.Beat`；15 秒没有新心跳 → 自动倒黑匣子并写明最后处理的文件。
上一个死循环正是这种"没有异常、只是不动"，现在会自己交出现场。

### 体积

| 场景 | 磁盘 |
|---|---|
| 4 个文件导入 + 补波形 | 4.1 KB（实测） |
| 4213 个文件全库扫描 | ~40 KB |
| 10 万文件 | ~0.5–1 MB |

### 按时间窗导出

- 界面：10 / 20 / 30 分钟、1 / 2 小时、1 天、全部；可勾「只导出警告和错误」；实时预估行数与体积
- 命令行：`--exportlog <zip> [分钟|all] [warn]`
- 包内容：`log.txt`（裁剪后）、`failures.csv`（按列拆开的失败行）、`system.txt`、`readme.txt`

### 修复：导出日志对话框看不清

- **现象**：勾选框是白框、旁边文字看不见；1 小时/1 天选项实际按 1 分钟算。
- **原因**：`CheckBox` 用 WPF 默认模板（浅色 + 深色字）放在深色窗口上；`Tag="1h"` 用 `int.TryParse` 解析失败后落到默认 30 分钟。

### 修复：语言切换完全没反应（三个原因）

| # | 原因 | 修复 |
|---|---|---|
| 1 | `ApplyTo` 遍历时把 `RowDefinition` 当节点，抛 `不是 Visual` → 遍历中断，`applied=0` | 可视树 + 逻辑树双走，非 Visual 节点安全跳过 |

| 3 | 设置窗口自己从没套过语言 | 进设置套一次，切换时**立即预览**（设置 + 主窗口同时刷新） |

## 第 8 批 · 自然排序

### 现象

文件夹按名称排序时 `10_User Interface Sounds` 排在 `1_Weapon Recordings` 前面。

### 原因

纯字典序比较：第二个字符 `'0'(0x30)` < `'_'(0x5F)`，所以 `10_` 永远在 `1_` 前。字符串比较不会把 `10` 当"十"。

### 修复

新增 `Services/NaturalComparer.cs`：遇到连续数字时读完整段当数字比（去前导 0 → 比位数 → 比数值），其余字符照常忽略大小写比较。

三处排序全部替换：内容区文件夹卡片、左侧文件夹树、按名称排序的列表/网格。

实测 `1_ 2_ 3_ 6_ 7_ 8_ 9_ 10_ 11_ 100_` 顺序正确。

## 第 9 批 · 多声道降混

### 现象

5 声道（5.0）的 WAV 素材能播了，但听起来「少了东西」——环境声还行，对白/打击类素材明显空。

### 原因

- 解码后 `channels > 2` 时只取了前两轨：`FL` 和 `FR`，中置（人声/主要声源）和环绕整条丢弃
- 顺带发现 `WavReader` 读 `FormatTag` 用 `ReadInt16()`，`0xFFFE` 被符号扩展成 `-2`，导致 Extensible 分支从未执行，通道掩码永远读成 0

### 修复

| 项 | 做法 |
|---|---|
| 通道掩码 | `fmt = br.ReadInt16() & 0xFFFF`，5.0 文件实测读到 `0x37`（FL｜FR｜FC｜BL｜BR） |
| 降混 | 新增 `Audio/Downmix.cs`：按掩码逐通道加权（FL/FR 1.0、FC 0.707、环绕 0.707、LFE 0.5） |
| 限幅 | 叠加后峰值超过 0.999 时整体缩一次，避免削波（实测 6 声道满幅素材 2.62 → 0.999，增益 0.381） |
| 无掩码文件 | 按 FL,FR,FC,LFE,BL,BR 顺序猜；中置只有声的测试文件能混出 0.354 峰值（旧逻辑是 0） |
| 日志 | `[播放] 5ch (FL｜FR｜FC｜BL｜BR) → 立体声，限幅前峰值 0.35，增益 1.00` |

### 验证

| 测试文件 | 结果 |
|---|---|
| 5.0 真实素材（54 s） | 掩码 0x37，降混后 RMS 0.021 → 0.029、峰值 0.212 → 0.352（中置/环绕进来后能量变高） |
| 5.1 只有中置有声 | RMS 0.250、峰值 0.354（旧逻辑取 FL/FR 会是全静音） |
| 5.1 六轨满幅 | 限幅前峰值 2.623 → 增益 0.381 → 输出峰值 0.999，不削波 |
