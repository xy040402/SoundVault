# 音匣 SoundVault 1.0.0 → 1.0.2 更新汇报

> 素材稿：每条改动都写清楚「以前什么样 → 现在什么样 → 做了什么 → 怎么量出来的」，
> 数字都来自实测日志，可直接做成图表。

**版本节奏**：1.0.0 发布（11-01）→ 1.0.1 内部迭代（11-19 冻结，未对外）→ 1.0.2 发布（11-20）

**这一版的两条主线**：把该快的弄快；把该说清楚的弄清楚。没有加花哨功能，还删掉了三个。

---

## 一、导入：从"等它读完"到"两秒能用"

### 以前什么样

拖一个几百 MB 的音效包进来，进度条要爬很久。库越大越慢，而且慢得**和总字节数成正比**——30 GB 的库，第一次导入要好几分钟。第二次启动也要重新等一遍。

### 现在什么样

拖进去，进度条一闪，**卡片直接出来**，可以立刻点、立刻听。波形区先是平线，几秒后自己"长"成真波形。

### 做了什么

扫描被拆成两段：

| 阶段 | 干什么 | 什么时候跑 |
|---|---|---|
| ① 快扫 | 只读文件头：采样率、声道、位深、时长 | 导入 / 启动时增量扫描 |
| ② 补波形 | 查库里 `peaks` 为空的行，每批 200 个解码写回 | 扫完之后自动在后台跑 |

为什么以前会读整个文件：为了在卡片上画波形，必须拿到整段采样的峰值。这个需求本身没错，错在把它塞进了"扫描"这一步——用户等的是"库能不能用"，不是"波形好不好看"。

配套的几个细节：

- 补波形 **3 线程**，不抢播放和滚动
- 可以取消；也可以中途关软件，下次启动**接着补**（实测中断后剩 26,000 个自动续上）
- 波形峰值存进 SQLite（每行 512 字节），第二次启动不再算

### 怎么量出来的

同一个包（60 个 5 分钟 WAV，1.48 GB），两个版本各跑一次，读 `[扫描] 完成 … 用时=` 那一行日志：

| | 1.0.0 | 1.0.2 |
|---|---|---|
| 扫描完成 | 1709 ms | **20 ms** |
| 补波形 | （在扫描里） | 2512 ms，后台 |
| 10 万文件扫描 | — | 10.1 秒（约 0.1 ms/文件） |
| 10 万文件补波形 | — | 18.1 秒（5,500 个/秒） |
| 10 万文件二次启动 | — | 675 ms |

## 二、搜索：从"一个字一个字地卡"到"敲完就出"

### 以前什么样

在搜索框里打 `b`、`bd`，每打一个字符，界面要顿一下；库大的时候能明显看到列表"闪一下才出来"。

### 现在什么样

连打三个字的反应和打一个字差不多，结果几乎是跟着手指出来的。

### 做了什么

原来每敲一个键都要：读全库（连波形 BLOB 一起读）→ 重新造一遍卡片对象 → 全量过滤 → 按中文排序。四件事都是 O(全库)。

改成了四件事：

| 手段 | 解决什么 |
|---|---|
| 整库缓存 | 卡片对象只造一次，存在内存里；换库、扫描完成、导入、删库才失效 |
| 拼音预热 | 建缓存时并行把首字母和全拼算好，避免第一次打 `bd` 卡一下 |
| 逐字增量 | 新关键字是上一次的前缀、排序没变 → 只在上一次的结果里再筛 |
| 输入防抖 | 110 ms；连打五个字只算一次 |
| 后台预热 | 启动后就在后台把缓存建好，第一次点搜索不用等 |

### 怎么量出来的

10 万条数据，每项跑 5 次取最优：

| 指标 | 1.0.0 | 1.0.2 |
|---|---|---|
| 拼音首查（`bd`） | 49 ms | **1 ms** |
| 首次进搜索（缓存命中） | 150 ms | 53 ms |
| 逐字增量 | 每次全库 7 ms | 2 ms |
| 缓存构建（后台，用户不等） | — | 1,021 ms |

## 三、界面：三处"看着别扭"的地方

### 1. 进度条

**以前**：一条半透明横线，从头到尾看不出在动。原因很具体——填充元素没写宽度，缩放倍率乘在了一个宽度为 0 的元素上。

**现在**：两行。

```
正在补齐波形图，您可以继续操作
22 / 40　56%　·　剩余 2 秒　·　AK47_BURST_20.wav  ━━━━━━━━  [取消]
```

第一行回答"在做什么、能不能继续操作"，第二行是进度本身。各阶段文案分开：枚举文件 / 比对索引 / 读取音频头 / 写入索引 / 补齐波形。

### 2. 文件夹和音效同屏

**以前**：一个目录里既有子文件夹、又直接放着音频时，右边**只显示文件夹**，那些音频要切到「全部音效」才找得到。

**现在**：上面一排文件夹卡片（最多约两行，多了自己滚），下面是根目录的音频卡片，统计写「3 个文件夹 · 5 个音效（根目录）」。

### 3. 滚动

**以前**：滚一格，画面直接跳到新位置，中间什么都没有。

**现在**：逐帧缓动（ease-out），120–220 ms。左侧栏和右侧网格都做了。设置里可以关掉，也能选快 / 标准 / 缓三档，并跟随 Windows「显示动画」的系统开关。

同时修了三个滚动相关的 bug：

| 现象 | 原因 |
|---|---|
| 换文件夹后底部一大片空白 | 沿用了上一个视图的滚动位置 |
| 某些页面滚轮几乎滚不动 | 面板 `extent`（可滚动高度）算成 0 |
| 补波形结束卡 1–2 秒 | 补完把整库卡片重建了一遍 → 改成只贴回可见卡片（5 千库 28 ms） |

## 四、范围与归属：快捷入口改成跨库

**以前**：点「全部音效」，看到的是**当前选中的那个库**。两个库的人想找"我所有的雨声"，只能一个个库点过去。

**现在**：

| 入口 | 范围 |
|---|---|
| 全部音效 / 收藏 / 最近导入 / 最近播放 / 标签 / 重复检查 / 搜索 | **全部库** |
| 侧栏的库 / 文件夹 | 只看该库（面包屑能看出来） |

搜索也跟着跨库了——以前搜索只在当前库里找，多库时会漏。

## 五、安装与设置

### 安装器

- 全程向导式页面，**不再弹 Windows 原生对话框**（关旧版本、卸旧版本、删数据确认都在页面里）
- 装在受保护目录会自动提权；装完可以直接启动
- **开始菜单快捷方式**：以前勾了不一定出现（建在嵌套目录里，也没校验）。现在直接放 `Programs\` 根，装完用 `File.Exists` 校验，失败退回 WScript 再建一次
- 卸载可选「保留数据」或「彻底删除」，删数据有二次确认

### 设置面板

左导航 + 五页：

| 页面 | 内容 |
|---|---|
| 常规 | 主题、窗口置顶、平滑滚动、重看新手引导 |
| 外观 | 主色（6 预设 + HEX）、最近使用 8 个、收藏 10 个、面板强度、圆角、云母 |
| 导出与命名 | 命名模板、文件名清洗规则、文件关联 |
| 数据与日志 | 数据位置、重建索引、备份数据、便携模式、日志、诊断包 |
| 关于 | 版本、数据目录、反馈入口 |

外观不再是独立对话框，改成页面内即时预览，点「取消」全部还原。

## 七、删掉的三个功能

| 功能 | 为什么删 |
|---|---|
| **「已用」角标** | 判定依赖播放记录，删库/重导入后残留；逻辑本身不可靠 |
| **省电模式** | 限制 60 fps 治不了根。掉帧的真正原因是卡片实例化成本，改成优化源头 |
| **AI 自动打标签** | 本地 YAMNet 对真实录音（雨声、鸟叫）能认，但对拟音/合成音效准确率不够——"拔刀"被识别成"玻璃破碎"。错标签比没标签更麻烦，连 15 MB 模型一起删了，exe 从 93.2 MB 回到 73.4 MB |

## 九、兼容与升级

- **覆盖安装**：会自动关掉正在运行的音匣，数据（`store.json` / `index.db`）保留
- **老库不用重新导入**：之前算过的波形不会重算
- **便携模式**：exe 旁边有 `data\` 就用它
- **新增配置项**：`ScrollAnim`、`ScrollAnimMs`（旧配置读进来自动补默认值）

## 十二、可能被问到的问题（备查）

| 问 | 答 |
|---|---|
| 为什么波形不能一起算好？ | 能，但等于把整段采样读一遍，库越大越慢。波形是"锦上添花"，先让库能用更重要 |
| 补波形会不会卡？ | 3 线程、每批 200 个，实测滚动和播放不受影响；也能取消 |
| 为什么删 AI 打标签？ | 模型能认真实录音，认不了拟音/合成音效。给错标签比不给更麻烦 |
| 10 万个文件真的能用吗？ | 扫描 10 秒、搜索 2 ms、滚动 52–97 fps，测过 |
| 会不会动我的文件？ | 只建索引，不移动、不复制、不修改；删库只删索引和它自己记的状态 |
| 老库需要重导吗？ | 不需要，波形不会重算 |
