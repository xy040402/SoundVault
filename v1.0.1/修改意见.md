### P8｜日志系统：所有排查的地基

**现象**：用户报"打不开""装不上"，能拿到的信息只有一句话和一张截图。

**根因**：
- 现在只有崩溃时写 `%TEMP%\sv-crash.txt`（`App.xaml.cs:37-58`），用户找不到
- 扫描、播放、安装的失败信息**全部被 catch 吞掉**（例如 `WavReader.TryRead` 直接 `return null`）

**为什么排第一**：P6、P7 现在都只能靠猜。没有日志，修 bug 等于赌博。

**方案**：完整设计见 **第 3 节**。

**验收标准**：
- 打开程序 → 日志文件出现在 `%LocalAppData%\SoundVault\logs\`
- 故意喂坏文件 → 日志里有「哪个文件、什么格式、什么异常」
- 设置 →「导出诊断包」→ 得到一个 zip，里面日志+系统信息
- 崩溃时日志最后一行能看到异常堆栈（且不丢）

**工作量**：2 天 ｜ **版本**：v1.0.1

### P1｜导入进度：不是没有，是"看不见"

**现象**：导入大文件夹时界面像卡住，不知道在干什么、还剩多久。

**根因**（`Services/Indexer.cs`）：

| 阶段 | 现状 | 问题 |
|---|---|---|
| ① 枚举文件（第 52 行） | `Total = 0`，只显示「正在枚举文件」 | **没有数字**，几万文件时几分钟不动 |
| ② 与索引比对（第 61 行） | 无进度 | 大库 `Stamps()` 读全表，可能几秒 |
| ③ 解析（第 91–109 行） | 有百分比，每 120ms 刷一次 | 这个其实是对的 |
| ④ 写库（第 121 行） | 无进度 | 一次性事务，大库要几秒 |

**方案**：
1. 枚举阶段也报数：`已找到 12,340 个文件…`（每 500 个刷一次）
2. 解析阶段显示：`12,340 / 30,221 · 雷声_96k.aiff · 预计剩余 1 分 20 秒`
3. 写库阶段：`正在写入索引…`
4. 全程一个 **「取消」按钮**（`CancellationToken` 已有，接到 UI 上即可）
5. 进度条放在**主界面顶部固定位置**，不放在弹窗里（弹窗会自动关，用户看不到）

**验收**：
- 故意用 `SV_SLOW_SCAN=1` 慢放，能看到四个阶段的文案依次变化
- 中途点取消 → 已解析的部分不写库，界面回到导入前状态
- 剩余时间估算误差 < 30%

**工作量**：0.5 天（不含 P2 的重构）｜ **版本**：v1.0.1

#### ✅ 完成情况（v1.0.1，2026-11-19）

| 项 | 做法 |
|---|---|
| 枚举阶段报数 | `Indexer.Scan` 每 180ms 上报一次 `已找到 N 个文件`（`Total=0`，进度条走跑马灯） |
| 比对阶段 | 新增「正在比对索引」一帧 |
| 解析阶段 | `已完成 / 总数 · 百分比 · 剩余时间 · 当前文件名` |
| **整条进度** | 0 → 8%（枚举完）→ 96%（解析完）→ 100%（写库）；百分比直接写在文字里 |
| 修显示 bug | 填充条原来没写 `Width`，DesiredSize=0，`ScaleX` 放大也还是 0 → **看着永远不动**。补 `Width="150"` |
| 取消按钮 | 进度条右侧「取消」→ `_scanCts.Cancel()`；解析阶段取消**不写库**，界面回到原状并提示「已取消扫描」 |
| 测试钩子 | `SV_SLOW_SCAN=1` 每文件睡 25ms；给数字则按毫秒（`SV_SLOW_SCAN=120` 便于观察） |

**实测**

| 场景 | 结果 |
|---|---|
| 300 个文件（`SV_SLOW_SCAN=120`） | `50 / 300 23% · 剩余 2 秒` → `144 / 300 50%` → `282 / 300 91%`；进度条肉眼可见地在填 ✅ |
| 中途点取消 | 日志：`用户点了取消` → `解析阶段取消，已完成 88/200` → `扫描返回 文件数=0`（**没写库**）✅ |
| 正常速度 200 个文件 | 枚举 1ms，解析+写库共 **73ms**（回归无变慢）✅ |

> 坑：`Border` 不进 UIA 自动化树，点不到 → 把点击事件挂到里面的 `TextBlock` 上（顺带对无障碍也更友好）。

### P2｜大库导入慢：根因是"为了画波形读了整个文件"

**现象**：3000 个文件约 10 分钟；百万级不可用。

**根因**（`Services/Indexer.cs:139-163`）：

```csharp
var info = WavReader.TryRead(path);          // 读文件头：微秒级，没问题
row.Peaks = WavReader.ComputePeaksQuantized(path, info);  // ← 把整个文件流式读完（512 根柱子）
```

实测吻合：10 分钟 / 3000 文件 ≈ **200 ms/文件**，就是整文件读取的成本。

**关键认知**：Everything 快是因为它**只读文件系统元数据**，从不打开文件。而时长/采样率/波形都必须读文件内容 —— 所以"用 Everything 的方式"不能直接解决这个问题，**必须把"读内容"从导入流程里拆出去**。

**方案：两阶段索引**

| 阶段 | 做什么 | 3000 文件耗时 |
|---|---|---|
| **A. 立即可用** | 枚举 + 读文件头（时长/采样率/声道都在头里）+ 写库 | **< 5 秒** |
| **B. 后台补波形** | 低优先级线程算波形，算好一张刷新一张卡片 | 后台慢慢来 |
| **B'. 可见优先** | 用户滚到哪，先算哪几屏（插队） | 立刻可见 |

**数据模型改动**：
- `index.db` 加一列 `wave_state`（0=未算 / 1=已算 / 2=失败）
- 卡片显示「波形加载中」的占位（骨架条），算好后替换
- 迁移策略：老库启动时自动补齐该列，`wave_state` 默认 0，后台补算

**目标指标**（发布说明里写出来）：

| 场景 | 现在 | 目标 |
|---|---|---|
| 3,000 文件导入 | ~10 分钟 | **< 15 秒**出全部卡片 |
| 10,000 文件 | 不可用 | **< 60 秒** |
| 100,000 文件 | — | **< 10 分钟**（A 阶段） |

**顺带**：加「大库模式」开关（>20,000 文件默认不预计算波形，只算可见）。

**验收**：
- 3,000 文件导入，全部卡片出现 < 15 秒，且卡片立刻可悬停试听
- 滚到哪，2 秒内出波形
- 关掉程序再开，已算的波形不重算
- 老版本 `index.db` 能自动升级，不丢评分/标签/集合

**风险**：这是本项目**最大的一次结构改动**，要改 DB schema + 卡片渲染状态 + 后台队列。必须做迁移测试。

**工作量**：4 天 ｜ **版本**：v1.1

### P6｜96k 无法播放：找到两个真问题

**现象**：用户报"导入的 96k 文件无法播放"。

**根因 A（确定是 bug）** —— `Audio/AudioClip.cs:74-83`：

```csharp
".wav" or ".aif" or ".aiff" => new WaveFileReader(path),
```

**AIFF 是大端格式，而 `WaveFileReader` 只认 RIFF/WAVE（小端）** → 所有 `.aif/.aiff` 都播不了。而 96kHz 素材在专业音效库里非常常见 AIFF。

**根因 B（可能）** —— 我们的头解析器 `WavReader.TryRead` 要求文件以 `RIFF` 开头，且 `data` 长度 > 0：

| 情况 | 结果 |
|---|---|
| RF64（>4GB） | 解析失败 |
| W64 / CAF | 解析失败 |
| data 长度写成 0（流式写入） | 解析失败 |
| 96k 24bit PCM | ✅ 支持 |
| 96k 32bit float | ✅ 支持 |
| WAVE_FORMAT_EXTENSIBLE | ✅ 支持（第 66–72 行） |

所以"96k 播不了"很可能是**容器/封装**问题，而不是采样率问题。

**方案**：
1. **按内容判断解码器，不按扩展名**：先嗅探 `RIFF`/`RF64`/`FORM`(AIFF) 魔数 →
   - RIFF/RF64 → `WaveFileReader`
   - AIFF → `MediaFoundationReader`（系统自带，支持 AIFF）
   - 其它 → `MediaFoundationReader`，失败再 `Mp3FileReader`
2. **播放失败要说原因**：不再静默，"此文件格式不支持（AIFF / 24bit）" 或 "文件被其它程序占用"
3. 索引阶段失败的文件标 `wave_state=2` + 记录原因，界面卡片显示 ⚠ 角标，鼠标悬停看原因
4. 测试样本加入：96k 24bit / 96k float / AIFF / 空 data 头 / RF64

**验收**：
- 用 96k 24bit WAV、96k float WAV、AIFF 各一个 → 都能播放
- 故意改名成 `.wav` 的 AIFF → 靠嗅探仍能播放
- 坏文件 → 弹出明确原因，日志有记录

**工作量**：1 天 ｜ **版本**：v1.0.1

#### ✅ 完成情况（v1.0.1，2026-11-19）

**根因确认**：AIFF 被交给只认 RIFF 的 `WaveFileReader`，所以所有 `.aif/.aiff` 都播不了。
另外实测发现：**96kHz 的 WAV（16/24/32/float32）本来就能正常播放**，所以用户报的"96k 打不开"更可能是 AIFF 或其它容器。

| 项 | 做法 |
|---|---|
| 容器嗅探 | 新增 `Audio/AudioProbe.cs`：读前 12 字节判 RIFF / RF64 / AIFF / AIFC / 未知 |
| AIFF 解码 | 新增 `Audio/AiffReader.cs`：自己解析 FORM / COMM / SSND，大端 PCM 转小端（本机 MediaFoundation 对 AIFF 直接报 `0xC00D36C4`，靠不住） |
| 解码器选择 | `AudioClip.CreateReader` 按内容走：RIFF→WaveFileReader，AIFF→AiffReader，其余→MediaFoundation，mp3 先试 Mp3FileReader |
| 索引兜底 | `Indexer.ReadFile`：非 RIFF 时用 AiffReader / MediaFoundation 读时长、采样率、位深，并算 512 点波形 |
| 失败要说原因 | `AudioClip.LastError` + `FriendlyError()`：文件不存在 / 没权限 / 被占用 / 不是音频 / 没有音频数据 |
| 界面提示 | 悬停或播放按钮失败时，播放条文案 + Toast 显示具体原因 |

**实测（`tools/verify-decode.ps1`，14 项全通过）**

| 样本 | 结果 |
|---|---|
| AIFF 44.1k/16bit | `44100 Hz / 2 ch / 1500 ms` ✅ |
| AIFF 96k/24bit | `96000 Hz / 2 ch / 1000 ms` ✅ |
| WAV 96k/24bit、float32、32bit | 全部正常 ✅ |
| 坏文件（随机字节） | 拒绝 + 原因「不是可识别的音频文件」✅ |
| data 长度为 0 | 拒绝 + 原因「文件里没有音频数据」✅ |
| 真实播放（`--playtest` AIFF） | `wasapi started = true`，播放位置在前进 ✅ |
| 索引 | 日志：`AIFF 已解析 时长=1500ms 波形=512 点`；`完成 total=8 失败=2` ✅ |

**顺带发现的新问题**：库里音频文件直接放在根目录、没有子文件夹时，库视图显示「0 个文件夹 · N 个音效」但**内容区空白**，必须点「全部音效」才看得到 → 记为 **P13**。

### P7｜安装 "unknown hard error"

**现象**：安装时 Windows 弹 unknown hard error，没有其它信息。

**可能原因（按概率）**：

| 原因 | 概率 | 判断依据 |
|---|---|---|
| 杀软/Defender 拦截单文件 exe 的**自解压**到 `%TEMP%` | 高 | 日志停在「解包主程序」 |
| UAC 提权被拒 / 策略禁止 | 中 | 日志停在「请求提权」 |
| 磁盘空间不足 / `%TEMP%` 被限制 | 中 | 日志有写入失败 |
| 目标路径含特殊字符或过长 | 低 | 日志有路径 |
| 我们自己抛了未捕获异常 | 中 | 崩溃日志有堆栈 |

**方案**：
1. 安装器全程写日志（同 P8，另一份 `setup-*.log`）
2. 失败时弹窗不再是裸错误，而是：**「安装失败：写入文件时出错（错误码 5）」+「复制诊断信息」+「打开日志目录」**
3. 自解压失败时**回退方案**：改从 `%LocalAppData%\Temp` 解包，并在日志里说明
4. 安装前做预检：磁盘空间、目标目录可写、进程占用，任一不满足**提前**给友好提示

**验收**：模拟三类失败（只读目录 / 无权限 / 空间不足），每种都能给出可读的原因。

**工作量**：0.5 天（写代码）+ 等用户回传日志定位 ｜ **版本**：v1.0.1

### P5｜"是索引还是复制" —— 回答是对的，但要给证据

**结论**：**只索引，不复制、不移动、不改名**。

**证据**：导入流程 `AddLibraryAsync → Indexer.Scan → 写 index.db`，**全程序只有两处会复制文件**：

1. 导出（用户主动点，复制到指定目录）
2. 备份数据（只复制 `store.json` 和 `index.db`，不含音频）

**方案（低成本、高信任收益）**：
1. 导入对话框加一行：**「只建立索引，不移动、不复制你的文件」**
2. 说明书「导入素材包」章节第一段写同一句
3. 设置里加「数据位置」说明：库里存的是**路径**，不是文件
4. 右键菜单已有「在资源管理器里显示」→ 用户可亲眼确认文件还在原处

### P4｜AI 自动打标签

### P13｜库根目录直接放文件时，库视图空白

**现象**：库里如果音频文件直接躺在根目录（没有子文件夹），库视图显示「0 个文件夹 · 8 个音效」，但内容区**一张卡片都没有**；点左栏「全部音效」才看得到。

**验收**：准备一个只有平铺文件的库 → 点左栏该库，直接看到文件卡片，不用再点「全部音效」。

**工作量**：0.5 天 ｜ **版本**：v1.0.1

## 3. 日志系统设计（P8 展开）

### 3.1 一条日志长什么样

```
2026-11-19 17:30:12.418 [INFO ] [扫描] 开始 root=D:\音效库\Demo音效 模式=增量
2026-11-19 17:30:12.902 [INFO ] [扫描] 枚举完成 files=3021 dirs=184 用时=484ms
2026-11-19 17:30:12.905 [INFO ] [扫描] 需解析 new=3021 changed=0 skip=0
2026-11-19 17:30:14.117 [WARN ] [解码] 解析失败 D:\…\雷声_96k.aiff 容器=AIFF 位深=24 采样率=96000 → 回退 MediaFoundation
2026-11-19 17:30:20.553 [INFO ] [扫描] 写入完成 rows=3021 失败=1 用时=7.65s
```

格式：`时间(毫秒) [级别] [模块] 内容`，内容是 `键=值`，便于人眼和程序读。

### 3.2 记录什么

| 分类 | 内容 | 时机 |
|---|---|---|
| **启动环境** | 版本、Windows 版本、.NET 版本、CPU 核数、内存、DPI 缩放、便携模式、数据目录 | 启动时一次（约 20 行） |
| **扫描/导入** | 路径、文件数、耗时、新增/更新/跳过、**失败文件+原因**、慢文件（>2s） | 每次扫描 |
| **解码/播放** | 打开失败的文件、容器/位深/采样率/声道、异常、音频设备名与设备采样率 | 失败时 + 首次播放 |
| **界面操作** | 导入库、删库、导出（数量+目标）、批量重命名（改了几个）、设置变更 | 每个动作 |
| **安装/卸载** | 目标路径、可写检查、提权结果、解包大小与耗时、写文件数、注册表/快捷方式、清理结果 | 每一步 |
| **异常** | 完整堆栈 + 当时正在做什么 | 任何未捕获异常（强制 flush） |

**不记录**：音频内容、用户其它目录内容、账号类信息；诊断包里可对 `C:\Users\<名字>\` 脱敏。

**不做的事**：不逐文件写日志（3000 文件会变 3000 行噪音）。成功只写汇总，失败才写明细。

### 3.3 什么时候写

| 时机 | 说明 |
|---|---|
| 启动 | 环境信息一次 |
| 事件驱动 | 每个动作「开始一行 + 结束一行（带耗时）」 |
| 异常 | 立即写并 flush（崩溃前必须落盘） |
| 退出 | 写「正常退出」；**最后一行不是它就说明是异常退出** |
| 心跳（可选） | 每 5 分钟一行内存/句柄数，用于查泄漏 |

**绝对不写的时机**：鼠标移动、滚动、每帧重绘、每次试听（除非失败）。

### 3.4 文件与导出

```
%LocalAppData%\SoundVault\logs\
├─ app-2026-11-19.log      当前，上限 5 MB
├─ app-2026-11-18.log      …
└─ 最多 5 个，自动删最旧
```

安装器单独一份：`setup-2026-11-19.log`（安装器是另一个 exe）。

用户操作：
- 设置 →「打开日志目录」
- 设置 →「导出诊断包」→ `音匣诊断-20261119-1730.zip`
  ```
  diagnostics.zip
  ├─ app-2026-11-19.log
  ├─ system.txt          版本/系统/CPU/内存/缩放
  ├─ config.json         设置（脱敏）
  └─ crash.txt           如有崩溃
  ```

### 3.5 性能约束

- 写入走**后台队列**，UI 线程只入队，绝不阻塞
- 批量 flush（每 200ms 或 64 行），异常时立即 flush
- 单条日志 < 1 KB，超长内容截断（路径保留首尾）

### 3.6 实现要点（给未来的我）

| 项 | 做法 |
|---|---|
| 位置 | `Services/Log.cs` 单例，静态方法 `Log.Info/Warn/Error` |
| 现有 `L()` | `MainWindow.Sidebar.cs` 里的调试日志改成走 `Log.Info`（或删掉） |
| 崩溃 | 现有 `App.xaml.cs:37-58` 改为写正式日志目录 + 保留 `sv-crash.txt` 兜底 |
| 安装器 | Setup 项目里加一个精简版 Log（不能引用 App 的代码，两个独立程序） |
| 诊断包 | `System.IO.Compression.ZipFile`，无需额外依赖 |

### P14｜导入顺序：先扫描，扫完再出现

**现象**：拖入文件夹后，左栏**立刻**多出这个库、右边切到空视图，然后才弹进度条开始扫描。看着像"先建了个空库，再慢慢填"。

**根因**：`AddLibraryAsync` 的顺序是 `AddLibraryNode → ShowLibrary → ScanLibrariesAsync`。

**改法**：改成
1. 素材包识别（只读，不动界面）

### P15｜删库后重新导入，仍显示"已用"

**现象**：删掉一个库、再导入同一个文件夹，"已用"标记还在，评分/收藏也带着。

**已用是怎么判定的**：不是索引里的字段，而是 `store.json` 里的两张表 ——
`UsedAt`（标"已用"）和 `PlayedAt`（最近播放），按**文件绝对路径**记录时间戳；`UsedToday(path)` 判断是不是今天。
另外评分/收藏在 `store.Assets`（也是按路径），标签在 `index.db` 的 `asset_tags`。

**根因**：`RemoveLibrary` 只清了 `store.Libraries`、`LibraryNames` 和索引的 `files` 行，
**没清 `Assets` / `UsedAt` / `PlayedAt`，也没清 `asset_tags`**。重新导入时路径一样，旧状态原样命中。
（对话框里那句"评分、标签也会一起清掉"其实一直没兑现。）

**改法**
| 位置 | 做法 |
|---|---|
| `Store.PurgeLibrary(root)` | 按前缀清掉 `Assets` / `PlayedAt` / `UsedAt`，并把集合里的引用一并移除，返回各项数量 |
| `IndexDb.DropTagsUnder(dir)` | 删掉该目录下所有 `asset_tags`（LIKE + ESCAPE，路径里的 `_ % \` 都转义），再清理没人用的标签名 |
| `MainWindow.PurgeLibraryData(root)` | 上面两步 + 写日志，删库和测试钩子共用同一段代码 |

**实测**

| 步骤 | 结果 |
|---|---|
| 预先写入 1 条已用 + 1 条播放 + 1 条评分收藏 | `UsedAt=1 PlayedAt=1 Assets=1` |
| 跑清理（`SV_PURGE_TEST=1`，与界面删库同一方法） | `assets=1 played=1 used=1` |
| 清理后 | `UsedAt=0 PlayedAt=0 Assets=0` ✅ |
| 日志 | `[删库] 清理数据 评分收藏=1 播放记录=1 已用=1 集合引用=0 标签关联=0` |

### P16｜智能文件夹右键删不掉

**现象**：左栏"智能文件夹"右键没有反应。

**根因**：和集合（P8 之前的 v0.56）一模一样的两个坑 ——
1. 处理函数开头 `if (SmartList.SelectedItem is not SmartFolder f) return;`，右键**没选中**的行直接返回；
2. 事件挂在 `MouseRightButtonDown`，`ListBox` 内部把右键吃掉了，回调根本不触发。

**改法**：XAML 改成 `PreviewMouseRightButtonDown`；处理函数先用 `FindAncestor<ListBoxItem>` 找到鼠标下那一行并静默选中（`_suppressPickers`），再弹菜单。

**实测**：造一个智能文件夹 → 右键（该行原本未选中）→ 弹出「删除「4 星以上的武侠短音效」」→ 点击后行数 1 → **0** ✅

### P17｜移除「已用」角标

**要求**：这个功能不需要了，直接去掉。

### P7｜安装失败说不清原因（✅ 完成）

**社区那句话**：「装到一半弹 unknown hard error，不知道该删什么、也不知道该发什么给你们」。

**根因**：`Installer.Install` 是五段顺序动作（建目录 → 释放主程序 → 放卸载程序 → 建快捷方式 → 写注册表），
任何一段抛异常，界面上只有 `ex.Message` 一行；出问题的人既看不懂，也拿不出能定位的东西。

**改法**

| 项 | 做法 |
|---|---|
| 失败页 | 新增第 5 步「安装没有完成」：红叉 + **人话原因** + 精简详情（类型/错误码/消息/磁盘可用）+ 两个按钮 |
| 步骤上下文 | `Installer.Step("释放主程序", …)` 包住五段动作，异常变成 `InstallStepException`，界面能说"在「释放主程序」这一步失败" |
| 原因翻译 | 拒绝访问 / 路径太长 / 磁盘满（0x80070027、0x80070070）/ 文件被占用（0x80070020）/ 拒绝写入（0x80070005）/ 包损坏（释放主程序时空引用） |
| 提前拦截 | 安装前查磁盘可用空间（< 200 MB 直接报"磁盘空间不足"）；包里没有主程序时直接停在位置页并禁用「安装」 |
| 复制诊断信息 | 一键把「版本 / 系统 / 管理员 / 目标目录 / 失败步骤 / 完整异常 / 日志路径 / 最近 40 行日志」写进剪贴板 |
| 打开日志目录 | 直接 `explorer` 打开 `%LocalAppData%\SoundVault\logs` |
| 重试 | 失败页底部按钮变成「重试」，不用从头再走一遍 |

**实测（用 `SV_SETUP_FAIL=1` 模拟磁盘满）**

| 检查 | 结果 |
|---|---|
| 失败页文案 | 「磁盘空间不足。清理一下再装，安装需要约 200 MB。」✅ |
| 详情框 | `IOException（0x80070027）：…` + `磁盘 D:\ 可用：434842 MB`（不再暴露源码路径）✅ |
| 复制诊断信息 | 剪贴板拿到 1729 字符，含目标目录、失败原因、完整异常、日志路径、最近日志 ✅ |
| 日志 | `[ERROR] [安装界面] 安装失败 \\| IOException: …` 与 `[INFO] [安装界面] 已复制诊断信息 长度=1729` ✅ |
| 正常安装回归 | 静默安装成功；全量体检 **31/31 通过** ✅ |
