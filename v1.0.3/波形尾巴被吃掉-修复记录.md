# 波形尾巴被吃掉 · 排查与修复记录

> 版本：音匣 1.0.3
> 影响范围：列表视图 / 卡片视图的波形，以及右侧详情栏的波形
> 结论：**采样步长用整数除法，导致只画了音频的前 74%~98%**，宽度越大丢得越多

---

## 一、现象

同一个音效文件，名称列窄的时候波形有 **5 个起伏**，把名称列拉宽之后只剩 **4 个**，最右边那一段没了。

当时的截图（本地保留，未随仓库发布）：

| 截图 | 名称列右边缘 | 第一个音效的起伏数 |
|---|---|---|
| `1.png` | ~185 | **5 个**（1、4 大，2、3、5 小） |
| `5.png` | ~420 | **4 个** |
| `7.png` | ~555 | 4 个（第 5 个仍缺） |
| `11.png` | ~830 | 4 个 |

声仓（`a.png` ~ `f.png`）在同一拖动过程里起伏数始终不变——它的波形是**等比压缩**，我们是**丢尾巴**。

---

## 二、我走过的弯路（都是错的，记录在这免得再踩）

| 猜测 | 为什么错 | 花了多久才排除 |
|---|---|---|
| 名称列宽度绑定没生效 | 确实一度没生效（`ColumnDefinition` 不在可视树里，`RelativeSource AncestorType=Window` 找不到宿主），但修好后丢尾巴依旧 | 改了 3 版 |
| 虚拟化面板格子宽度算错（`VirtualizingWrapPanel` 用了上一轮视口宽） | 面板确实有这个毛病，改了 `ScrollOwner.ViewportWidth` 优先，波形仍然丢尾巴 | 1 版 |
| 行内容溢出行宽被裁 | 只有在名称列拉太宽时才会发生；把宽度夹住之后，丢尾巴依旧 | 1 版 |
| 几何缓存没跟着宽度重建 | 加了每帧核对，仍然缺 | 1 版 |
| 用缩放变换代替重算（声仓的做法） | 窄行里柱子互相重叠糊成一团，回退了 | 1 版 |

**为什么绕了这么久**：一直在看“宽度 / 布局 / 重绘”，没去核对“波形数据到底画了多少”。判断依据应该是最开始那张图里的**起伏个数**——它是与宽度无关的客观特征。

---

## 三、真正的根因

`Controls/WaveformView.cs` 里把 512 个峰值点压缩成若干根柱子，用的是**整数步长**：

```csharp
int target = Math.Clamp((int)Math.Round(w / 3.0), 20, peaks.Length);  // 柱子数
int per    = Math.Max(1, peaks.Length / target);                      // ← 整数除法

for (int i = 0; i < target; i++)
{
    int s0 = i * per;                       // 只走到 target * per
    int s1 = Math.Min(peaks.Length, s0 + per);
    // 取 [s0, s1) 的最大值画成一根柱子
}
```

`per` 是整数，`target * per` 通常**小于** `peaks.Length`，后面的点从来没参与计算。

### 覆盖率（peaks = 512）

| 波形宽度 | 柱子数 target | per | 实际取样点数 target×per | 覆盖率 |
|---|---|---|---|---|
| 217 px | 72 | 7 | 504 | 98% |
| 475 px | 158 | 3 | 474 | 93% |
| 700 px | 233 | 2 | 466 | 91% |
| 1140 px | 380 | 1 | 380 | **74%** |

所以：

- **窗口越宽，缺得越多**——这解释了“为什么拉宽才看出来”
- 用户那个文件 5 个起伏、末尾占约 20%，正好整个消失 → 变 4 个
- 窄窗口时覆盖率 98%，几乎看不出来，更容易被误判成“布局问题”

`Controls/SelectableWaveform.cs`（右侧详情栏）是同一份逻辑，同一个 bug。

---

## 四、修复

**按比例映射**，保证第 0 根柱子从第 0 个点开始、最后一根柱子到最后一个点结束：

```csharp
int s0 = (int)((long)i * peaks.Length / target);
int s1 = (int)((long)(i + 1) * peaks.Length / target);
if (s1 <= s0) s1 = Math.Min(peaks.Length, s0 + 1);
```

- 用 `long` 先乘再除，避免 `i * peaks.Length` 越界（512 × 数百没问题，但习惯上防一手）
- `s1 <= s0` 兜底一个点，防止柱子数多于点数时出现空柱子

改了两处：

| 文件 | 作用 |
|---|---|
| `Controls/WaveformView.cs` | 卡片视图、列表视图里的波形 |
| `Controls/SelectableWaveform.cs` | 右侧详情栏的波形 |

## 五、验证

测试文件：9 秒、0.35 Hz 包络（`pow(sin,3)`），肉眼可数 **7 个起伏**。

| 名称列宽度 | 修复前起伏数 | 修复后起伏数 |
|---|---|---|
| 200 | 5~6（尾部缺） | **7** |
| 700 | 5（尾部缺约 25%） | **7** |

截图：`griptest/sample-200.png`、`griptest/sample-700.png`（两张都是 7 个起伏，且最后一根柱子贴住右边缘）。

## 六、教训

1. **先读用户给的每一张图，再动手**。这次用户已经把 `1.png`（5 个起伏）和 `5.png`（4 个起伏）放在一起，等于把答案递到手上。
2. **找与现象无关变量无关的客观特征**（起伏个数、柱子数量、末根柱子位置）来自证，而不是靠“看起来像布局问题”。
3. 涉及采样/映射的代码，**先用一串小数据手算覆盖率**，比盯着界面猜快得多。
4. 不要一上来就靠“启动软件 + 截图”验证；能靠日志/数值算出来的先算。
